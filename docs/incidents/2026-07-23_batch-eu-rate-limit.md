# 障害調査記録: 日次バッチ処理時間の異常増加（EUリージョン追加後）

**記録日**: 2026-07-23
**対象ログ**: GitHub Actions実行ログ 2026-07-22 18:16:56〜（`actions-log_0-1000.txt` 抜粋分で調査）
**ステータス**: 対応完了（2026-07-23）

---

## 1. 問題事象

- GitHub Actionsで日次実行しているバッチ処理（差分更新）が、以前は1〜2時間で完了していた
- ドイツ語/フランス語UI対応およびEUリージョン（EUR通貨）の価格取得を追加して以降、実行時間が跳ね上がり、GitHub Actionsの上限である6時間を超過するようになった

---

## 2. 関連する変更

- `updater/constants.py` の `DEFAULT_REGIONS` が `['JP', 'US']` から `['JP', 'US', 'EU']` に変更された（EUはドイツを代表地域として使用、`steam_cc='de'`, `itad_country='DE'`）
- GitHub Actionsワークフロー（`.github/workflows/kv-updater.yml`）は `--regions` 指定なしで `main.py` を実行するため、この3リージョンがデフォルトで使われる

---

## 3. 調査で判明した事実（ログ根拠）

実行ログ（2026-07-22 18:16:56開始）を時系列で確認した結果:

| 時刻 | フェーズ | 結果 |
|---|---|---|
| 18:17:05〜18:18:15 | JPのITADバッチ取得（51バッチ） | 正常完了、10074/10078件取得。429エラーなし |
| 18:18:15〜18:19:36 | USのITADバッチ取得 | batch 1〜49は正常。batch 50, 51で429（レート制限）連発、3回リトライも失敗 → 9796/10078件取得（278件欠落） |
| 18:19:36〜18:22:46 | EUのITADバッチ取得 | batch 1から即座に429連発。batch 1〜24（約4800件相当）が軒並みリトライ失敗 → batch 25以降でようやく回復 → 最終的に5471/10078件しか取得できず（**4607件がEUデータ欠落**） |
| 18:22:46〜 | Phase 1比較ロジック | EUデータが欠落している約4607件全てで `No ITAD deal data ... Region: EU, will fetch from Steam API only` が出力され、`price_changed = True` と誤判定。本来Steam API再取得が不要なゲームまで大量にPhase 2（重い個別取得処理）へ回された |

---

## 4. 根本原因

### 4-1. レート制限超過（直接原因）

JP→US→EUと3リージョン分のITADバッチ取得を約5〜6分の間に連続実行しており、リクエスト総量（51バッチ×3リージョン＝153リクエスト）が増えたことで、後発のリージョンほどITAD APIのレート制限（429）に当たりやすくなっていた。

- `updater/itad_client.py` の `get_batch_deals` は、バッチ間に `time.sleep(random.uniform(1.0, 1.3))` の待機のみ（`itad_client.py:114-115`）
- リージョンをまたぐ際の待機はゼロ
- 429時のリトライは最大3回、バックオフ2秒→4秒（計6秒程度）で打ち切り（`itad_client.py:44-53`）。実際のレート制限解除に対して待機時間が不足しており、バッチ（200件単位）が丸ごと失敗扱いになっていた

### 4-2. ロジックの設計上の欠陥（増幅要因）

`updater/game_data_builder.py:479-493` の差分比較ロジックは、「ITADから当該リージョンのデータが取得できない」場合、一律で `price_changed = True` とみなしてSteam APIでの個別再取得（Phase 2）に回す設計になっている。

このロジックは本来、「ITADがそのゲームの当該リージョンデータを恒久的に持っていない」ケース（地域制限で販売されていない等）への正当なフォールバックとして設計されていたが、以下の2つの状況を区別する手段がない：

| ケース | 挙動 | 本来あるべき扱い |
|---|---|---|
| (a) ITADがそのゲーム/地域のデータを恒久的に持っていない | `itad_deal_maps[region].get(itad_id)` が `None` | Steam APIでフォールバック取得（正しい・現状の挙動） |
| (b) 今回の実行でITADバッチ取得自体が429で失敗し、そのチャンクが丸ごと欠落した | 同じく `None` | 本来は「不明」として扱い、KVの既存データを維持すべき |

上記4-1のレート制限により(b)が大量発生し、(a)と区別されずに全て「価格変更あり」として処理されたため、本来数十〜数百件程度で済むはずのPhase 2処理が数千件規模に膨れ上がり、実行時間の暴走（6時間超過）につながった。

---

## 5. 修正方針（合意済み・未実装）

### 方針1: ITAD APIリクエスト頻度の緩和

対象: `updater/itad_client.py`

| 項目 | 現状 | 変更案 |
|---|---|---|
| バッチ間の待機（`get_batch_deals`内） | 1.0〜1.3秒 | 2.0〜3.0秒程度に延長 |
| リージョン切り替え時の待機（`game_data_builder.py`のリージョンループ） | なし | 各リージョンのバッチ取得完了後に数秒〜十数秒の待機を追加 |
| 429リトライのバックオフ（`_request_with_retry`） | 2秒→4秒（計2回、約6秒で諦め） | 待機時間を延長し、リトライ回数も増やす（例: 5秒→15秒→30秒） |

### 方針2: 「取得失敗」と「本当にデータがない」の区別

対象: `updater/itad_client.py`（`get_batch_deals`）、`updater/game_data_builder.py`（`_rebuild_differential_update` Phase 1比較部分）

1. `get_batch_deals` が、バッチリクエスト自体が失敗した（429/通信エラーで諦めた）チャンクに含まれるIDの集合を、戻り値に追加して返すようにする
2. Phase 1比較ロジックで、`itad_deal` が `None` の場合に、そのIDが取得失敗リストに含まれるかどうかで分岐する：
   - 取得失敗リストに含まれる（今回の取得が失敗しただけ） → 「変更なし」として扱い、KVの既存データを維持（Steam再取得の対象にしない）
   - 含まれない（ITADに本当にデータがない） → 従来通り「変更あり」として扱い、Steam APIでデータ構築（`noItadData: true`）

## 6. 対応完了（2026-07-23）

方針1・方針2ともに実装済み。

### 実装内容

**方針1: ITAD APIリクエスト頻度の緩和**（`updater/itad_client.py`）
- `_request_with_retry` の429リトライ回数を3回→5回に増加（バックオフ 2秒→4秒→8秒→16秒、計最大30秒まで待機してから諦める）
- `get_batch_deals` 内のバッチ間待機を1.0〜1.3秒→2.0〜3.0秒に延長
- `game_data_builder.py` の3箇所（差分更新モード / 新規追加モード / バッチモード）全てで、リージョンを切り替える際に5秒の待機を追加

**方針2: 「取得失敗」と「本当にデータがない」の区別**（`updater/itad_client.py`, `updater/game_data_builder.py`）
- `get_batch_deals` の戻り値を `dict` から `(dict, set)` のタプルに変更。第2要素は、バッチリクエスト自体が失敗した（429/通信エラーで諦めた）チャンクに含まれていたITAD IDの集合
- 差分更新モード（`_rebuild_differential_update`）のPhase 1比較ロジックで、当該リージョンのITADデータが見つからない場合に、取得失敗リストに含まれているかどうかで分岐:
  - 取得失敗リストに含まれる → その地域の比較をスキップし、KVの既存データを維持（他の地域の比較は継続）
  - 含まれない（ITADに本当にデータがない） → 従来通りSteam APIでのフォールバック構築に回す
- 新規追加モード／バッチモードの呼び出し箇所は、戻り値がタプルになったことに合わせて受け取り方のみ修正（これらのモードには「既存データとの比較」という概念がないため、取得失敗リストの利用は対象外）

### 動作確認
- `python -m py_compile` で構文エラーがないことを確認
- `get_batch_deals` を単体でモックテストし、一部チャンクが失敗した場合に該当IDが正しく失敗リストに入ることを確認済み

## 8. 追加バグ修正（2026-07-24）: EU/US価格の小数点切り捨て

### 事象

方針1・2の対応後、2026-07-23の実行ではレート制限はほぼ解消（EU取得成功率 5471/10078 → 10070/10078）したものの、依然として6時間を超過。

### 原因

`updater/steam_client.py` の `_extract_price_from_api` が、Steam APIから取得した価格を`int()`で整数に切り捨てていた（`price_info['price'] = int(initial_price)` 等）。日本円（JPY）は小数点がないため問題にならないが、USD/EUR/GBPではセント/セント未満が切り捨てられる。

このバグは2025-10-13の最初のマルチリージョン対応コミットから存在（git履歴で確認済み）。ITADにデータがない場合のSteam APIフォールバック経由でのみ顕在化するため、レート制限修正でEUのITAD取得成功率が上がったことで、過去に切り捨てられて保存されたEU価格と正しいITAD小数価格との差分が大量に検出され、Phase 2（Steam再取得）の対象が膨れ上がる一因となっていた。

### 修正内容

`updater/steam_client.py` の `_extract_price_from_api` 内、`price`・`salePrice`の`int()`切り捨てを`round(x, 2)`に変更（小数点2桁を保持）。

### 動作確認
- `python -m py_compile` で構文エラーがないことを確認
- 単体実行で JPY=2500.0（整数のまま）、USD=19.99/9.99（セント保持）、EUR=24.5（小数保持）となることを確認

### 補足

既にKVに保存されている過去の切り捨て済みEU価格は、このコード修正だけでは直らない。該当ゲームのITAD取得が次回以降成功した時点で、Phase 2の上書き保存により順次正しい値に修正される（自然に解消していく想定）。
